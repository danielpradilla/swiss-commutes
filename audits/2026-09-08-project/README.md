Swiss Commutes project audit, 8 September 2026

Audited the current working tree, including its existing uncommitted changes. The review covered the application, route and statistical importers, tests, exported pages, accessibility, dependencies and public deployment headers. The user subsequently requested fixes for the confirmed bugs. Those fixes are local; this audit did not deploy the application.

The statistical unit is a home/workplace/mode/direction corridor, with estimated people rather than vehicles. The audit inspected 24,673 corridors across 16 locations. Geneva covers a canton; the other locations cover municipalities. City totals overlap and cannot be summed into a national count. Statistical reconciliation used the preserved source snapshots, not a fresh download of every source.

Validation after the fixes: 40 tests passed; all 748 data checks passed; lint, TypeScript and the production export passed. The additional export check verifies home/Zürich coverage equality, Geneva’s title and metadata. Updating Next.js and its ESLint configuration from 16.2.6 to 16.3.4 reduced npm’s reported vulnerabilities from three packages to zero. The initial strict audit had passed 715 of 716 checks.

Browser verification covered all 16 city pages during the audit, plus the home page. Follow-up checks verified equal home/Zürich statistics at 07:45, client-side city switching, reduced-motion startup, keyboard commune selection, keyboard time changes, empty mode selection and mobile layout. The final Geneva browser check had no console errors or warnings. Chromium was tested; Safari, Firefox and a physical mobile device were not.

Improvements in suggested order. Priority 1 was subsequently implemented locally; the others remain for discussion. The [performance follow-up](/Users/dpradilla/dev/swiss-commutes/audits/2026-09-08-project/performance.md) records measurements and validation.

| Priority | Improvement | Evidence and smallest useful next step | Effort |
| --- | --- | --- | --- |
| 1 | Reduce startup work and download size — implemented | Geneva HTML fell from 13.43 MB to 1.84 MB. The follow-up benchmark went from a 3.67-second main-thread task to at most 52 ms across three runs. Geometry loads separately and preparation yields to input. Total HTML plus geometry transfer is roughly unchanged; the complete export shrank by 64% by removing duplicated geometry from page exports. | Complete locally |
| 2 | Expand public-transport coverage where it is weakest | Routed shares of mapped transit estimates are 14.7% in Chiasso, 15.2% in Mendrisio, 29.6% in Lugano and 44.8% in Basel. Geneva is 91.3%. Extend the existing timetable importer to one of these regions, then load that city’s accepted cache. Route completeness does not validate allocated commuter counts. | Medium–large |
| 3 | Put route coverage beside the mode controls | The important denominators are currently inside a closed disclosure. Show each selected mode’s routed percentage near its control so users can judge the map before comparing modes or cities. | Small |
| 4 | Make data regeneration portable and complete | Four city modules (Basel, Lugano, Schaffhausen and La Chaux-de-Fonds) lack the current general generator path. Geneva and resident-mode imports hardcode dated source directories; timetable version metadata is also fixed in code. Add explicit input paths and source hashes, preserve the necessary inputs, and document a clean rebuild using pinned import tools. | Medium |
| 5 | Add a repeatable release check | Unit tests and source checks are substantial, but there is no repository CI workflow or durable browser smoke test. Automate `npm ci`, tests, lint, build and strict source audit; add a short browser check for navigation, filters and keyboard controls. Keep large source snapshots in an explicit fixture location. | Small–medium |
| 6 | Distinguish observed flows from allocated estimates close to the data | Non-Geneva foreign origins use population/distance allocation; Chiasso and Mendrisio reuse Lugano’s proportions. Resident-mode residuals can include modes besides walking/cycling. Show evidence type in commune details and retain an explicit unknown category where the source cannot identify active travel. Avoid adding invented confidence intervals. | Medium; better estimates require new evidence |
| 7 | Calibrate timing only if the intended use needs it | Every commuter currently travels in the same illustrative morning/evening waves, without attendance, holiday or shift adjustments. Rail fallback durations use a geographic heuristic. If the app will support factual traffic comparisons, acquire measured departure distributions and mode-specific travel evidence; otherwise keep the present illustrative framing. | Large/data-dependent |
| 8 | Remove obsolete code and build dependencies | The old logistic model, unused basemap variants, planned-city screen, unused configuration and Tailwind packages remain. Remove them in one focused cleanup with visual checks; retain the shared journey model, Leaflet and the existing route validation. | Small |
| 9 | Improve map readability and failure feedback | Map notes and legends use 8–9 px text. Tile loading has no visible failure state. Increase essential labels and show a concise message or use one tested fallback when the provider fails. | Small |

Startup performance is implemented. Transit coverage is the next larger product decision: choose whether to improve Basel or the Ticino cities first. The existing static architecture remains suitable; this review found no reason to introduce a backend, database or new application framework.
